RiceConnect — Migration Plan: Laravel/Render → Next.js/Supabase

Scoped against the standing 30-day competition calendar, not against an open-ended migration timeline. Executive decision confirmed: rebuild on the team's default stack — Next.js + Supabase + Prisma + Vercel, following the same pattern as the LikasLens migration.

From: rice-connect-v2 (Laravel 12 / Inertia / React / Render) To: Next.js + Supabase + Prisma + Vercel 11 dev days before mandatory capacity-building block

TL;DR

  • You're not designing this system from scratch — Karl's Laravel repo is a working, tested spec of the domain model. This is a port, not a rebuild-from-nothing, and the schedule below assumes that speed advantage.
  • Today (Sep 9) to Sep 20 is the entire dev runway before the mandatory capacity-building block. That's 11 calendar days to port five role modules, a tested money ledger, and auth. Full parity with Karl's repo in that window is not realistic — the plan below ports the wedge that carries the pitch and the pilot, and explicitly defers the rest.
  • Recommended cut, consistent with the competition-readiness review's own "narrow the wedge" call: ship Farmer + Miller + Ledger + Auth + Market Price Board for the pilot. Retailer and Driver modules, and the analytics dashboards, are real but not what 30 farmer interviews and a live pilot need on Oct 4.
  • The two critical bugs found in the architecture review (queued notifications with no worker; free-tier cold starts) don't get re-created in this migration if the plan below is followed — notifications go synchronous by default, and Vercel has no idle spin-down to begin with.
  • Branch/deploy convention carries over from LikasLens: main + development (+ staging if a preview environment is needed before the pilot), Vercel builds gated to the branches that matter.

3Porting the ledger — the part that has to be right

This is the one piece of Karl's system where a sloppy port costs someone real money. The Laravel version's guarantee — wallet.balance == sum(credits) - sum(debits), held by construction — needs to survive the move intact, not just look similar.

  • Schema: wallets(user_id, balance decimal(15,2)) and ledger_entries(user_id, amount decimal(15,2), type, reference_type, reference_id, description) — same shape, ported via Prisma migration with the same CHECK (amount > 0) constraint. Prisma's schema DSL doesn't express CHECK constraints natively — add it via a raw SQL migration step, same way the Laravel version had to for MySQL/Postgres.
  • Idempotency: keep the unique index on (reference_type, reference_id, user_id, type) as the real guarantee, not just an app-level pre-check. In Prisma, catch the unique-constraint violation (P2002) as the "already recorded" signal in addition to a pre-check — the pre-check is an optimization, the constraint is the actual source of truth, same division of labor as the original.
  • Atomicity: wrap debit+credit in prisma.$transaction(); use atomic increment/decrement (Prisma supports this natively) rather than read-then-write, exactly matching how the Laravel version avoided lost-update races.
  • Money type: use a decimal-safe library (e.g. decimal.js) or integer centavos in application code — this migration is the natural point to fix the float-typing note flagged in the architecture review rather than carry it forward.
  • Testing: port PaymentServiceTest.php's cases to Vitest, and port the spirit of ledger:check as a script that verifies the invariant against seeded data in CI. Run CI against a real local Postgres (Supabase CLI's local stack, or a Postgres service container) — this closes the gap the architecture review found in Karl's CI, which only ever tested against SQLite and never actually exercised the CHECK constraints.

4Auth & role enforcement

Five roles (farmer, miller, admin — retailer/driver deferred per §2), same as before. Supabase Auth handles identity; a role column on the user's profile table drives authorization, checked in Next.js middleware for page routes and again in each API route handler — the same "boring and consistent" pattern that made Karl's RoleMiddleware sound in the architecture review, not a new permissions framework. Don't reach for Postgres RLS as the enforcement layer unless you deliberately route DB access through a client that respects it (e.g. Supabase's client library with the user's JWT, not Prisma with a service-role connection) — RLS policies that Prisma silently bypasses are worse than no RLS, because they look like protection and aren't.

The honest risk in this schedule

11 dev days for Phases 0–3 is tight even for a port with a known-working spec to copy from. If Phase 1 (the ledger) runs long, the right move is to cut further into §2's "defer" list — not to compress testing on the money logic. A late pilot with a solid ledger is recoverable; a pilot that mishandles a farmer's payment during a live demo in front of judges is not.

6What's explicitly not in this plan

  • Retailer and Driver modules, and every analytics table — deferred per §2, revisit after Oct 7
  • A background job queue — deliberately not building one; revisit only if notification volume post-pilot actually justifies it
  • Postgres RLS as a real security boundary — not wired this round; the app-layer role check is the boundary, RLS can be layered on later as defense-in-depth once there's time to do it properly
